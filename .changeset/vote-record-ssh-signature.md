A committed vote record may now carry a `signature` — a detached `ssh-keygen -Y sign` signature, namespace `nexus-vote-record`, over the record's committed `hash` string — and the audit package exports the two halves of it (#3927 item 4, phases 1–2). `VoteRecordSchema` accepts the present-only `signature: { keyId, namespace, sig }` field outside the self-hash: a record hashes identically with or without it, no schema tier changes, and every existing record still parses and verifies. `verifyVoteRecordSignature({ record, allowedSigners })` checks a record against an OpenSSH `allowed_signers` text (validity windows honoured) and answers with one of five distinct codes — `signed`, `unsigned-record`, `unknown-signer`, `bad-signature`, `signature-not-measured` — never collapsing one into another; `signVoteRecordHash({ hash, keyPath, allowedSigners })` makes a signature whose `keyId` is the principal the file lists the key under. Both take an injectable `ssh-keygen` runner.

`scripts/append-ratification-record.ts` signs the committed hash after re-sequencing and re-hashing when `--signing-key <path>` or the new `NEXUS_VOTE_SIGNING_KEY` variable names a key; with neither it appends unsigned and prints one line saying so. A configured key the committed `governance/allowed_signers` does not list is refused (`signing-failed`) before anything is written. The governor ledger gate reports the verifier's code for every bound record on its evidence line (`signature: signed by williamzujkowski@nexus-agents`, `signature: unsigned-record`, …) without changing its exit code; enforcement past a committed cutover sequence is phase 3.

What a `signed` record proves is access to a listed private key from the environment that ran the append — not a human's presence. The audit hash-chain threat model states this with the measured example (an agent process signed a ledger commit with the operator's cached key, no prompt) and points at the custody follow-up, #6257.
