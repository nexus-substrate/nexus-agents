`pr_review` now decides what the voter panel reads and what the audit hash binds as two separate questions. Before, one comparison against the 50,000-byte hash cap decided both, so a diff over the cap was packed down to a security-prioritized subset even when every voter could have read it whole. The panel-read budget is now derived from the smallest context window across the panel's models in the model registry (gateway adapters, or each available CLI's default model), minus a 16,000-token prompt-overhead margin, converted at the shared token estimator's most conservative ratio (3.5 bytes per token); a 200k-token panel reads up to 644,000 bytes. If any model's window is unknown, the panel resolves to no models, or the panel is simulated, the budget falls back to the hash cap (the previous behaviour) and the reason is recorded. The hash binding is unchanged: the first 50,000 UTF-8 bytes. The response `coverage` object now carries `panelRead` (`full` | `partial`), `binding` (`full` | `prefix`), `reviewedBytes`, `boundBytes`, `totalBytes` (all UTF-8) and `budgetSource` (`registry` | `binding-cap-fallback`), and is present whenever either the panel read or the binding is not full. The ledger record's summary states both, e.g. `[panel read 61,204/61,204 bytes; binding covers first 50,000 bytes sha256:…; budget: registry (…)]`; the stamp is written before the PR title so the store's 500-character summary cap can no longer truncate it away under a long title. A verified approve is still degraded to `abstain` when the panel read is partial; when the panel read everything and only the binding is a prefix, the approve stands and the record discloses the prefix.
