`improvement_review` with `fileIssues: true` now files each issue with only the labels the target repository actually has, and says which requested labels it dropped.

The tool used to run `gh issue create --label p2,routing` unconditionally; in a repository without those labels the create failed and the signal was recorded under `issuesSkipped` as an error, so no issue was filed. It now runs `gh label list --json name --limit 1000` once per run (lazily, on the first create) and filters each issue's labels against that list. Every entry in `issuesFiled` carries `labelsDropped` (an explicit `[]` when nothing was dropped) and `labelCheck`: `'ok'` when the list answered, `'unavailable'` when `gh label list` itself failed, in which case the issue is filed with no labels and every requested label is listed as dropped, or `'truncated'` when the list filled its 1000-entry page, in which case no filtering is done, every requested label is passed and `labelsDropped` is `[]` (a label past the page cannot be told from a missing one). The label lookup never blocks the signal; a genuine `gh issue create` failure is still reported under `issuesSkipped` as before.

The target repository is now explicit. A new optional `targetRepo` input (`owner/repo`) is passed as `--repo` on every `gh` call the tool makes; when it is absent the tool resolves the working directory's remote via `gh repo view` and uses that. The response gains `issueTarget: { repo, source }`, where `source` is `'input'`, `'cwd-remote'`, `'unresolved'` (the lookup failed, so `gh` was left to its own cwd resolution and no `--repo` flag was passed) or `'not-filing'` (`fileIssues` was false). The `improvement-review` CLI prints the target and any dropped labels next to each filed issue. `FiledIssue` and `IssueTarget` are exported alongside `ImprovementReviewResponse`.
