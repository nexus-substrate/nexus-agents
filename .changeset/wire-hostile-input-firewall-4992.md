The two live untrusted-input paths, `issue_triage` and `pr_review`, now classify author trust through `HostileInputFirewall` (#4992). The firewall was a published API with zero production consumers: both paths called `classifyTrust()` directly, so no trust classification on any live path reached the security audit trail, and the maintainer allowlist the classifier reads from its config was never supplied — `isAllowlisted: false` was recorded on every result without being measured.

Behaviour under the default `NEXUS_FIREWALL_POLICY=off` is pass-through: the recorded `trustTier` and `userRole` are what the direct call produced for every author association, including injection-bearing content, because the shared instance is constructed with the new `contentDowngrade: false` option. The firewall's own classifier is content-aware (a Tier-2 author's injection-bearing body classifies as Tier 4), while the production paths classify by role and route content signals through reputation gating, which has its own rollout knob (`NEXUS_REPUTATION_GATING`); applying the same signal at classification too would have bypassed that knob. The sanitization stage still measures and records the injection flags; only the tier downgrade is withheld. The callers keep their own `evaluatePolicy` (Rule of Two per action) and their own reputation gating. Under `audit` the firewall reports `wouldRefuse` for the caller's real access posture and refuses nothing; under `enforce` a Rule-of-Two violation refuses the input as an error before any action is generated.

Trust classification events now reach the security audit trail on both paths — one `trust_classification` event per triage or review. In the MCP server the shared instance is wired to the process's durable, hash-chained `AuditLogger` at bootstrap (`configureUntrustedInputFirewall`, called from `registerMcpTools` with the logger `initializeAuditLogger` creates when `security.audit.enabled` is true). Where no durable logger exists — audit disabled, or the CLI `review` path — the firewall keeps the event only in its in-memory trail, which the next call clears, and says so: `FirewallResult.auditSink` and the `auditSink` field on both trust assessments read `'none'`. The other value is `'configured'`, deliberately not "delivered": it records that a durable `AuditLogger` was configured for the process and the event was handed to it; delivery to the hash chain is subject to that logger's own severity filter (trust events are `info`, so `security.audit.minSeverity: 'warning'` drops them), its bounded queue and its timed, fail-loud flush, and is not confirmed per call.

One reputation gate, one tier. The callers still measure reputation themselves (account age, comment history) but now pass it per call (`FirewallProcessOptions.reputation`) and consume the gate the firewall computes (`reputationGate`) instead of gating a second time. The firewall's Rule-of-Two signal, its `wouldRefuse` count under `audit`, and the trust audit event therefore all use the enforced tier the caller's policy gate acts on — previously the firewall evaluated the pre-reputation classifier tier, so a CONTRIBUTOR demoted by injection flags was blocked by the caller but counted as `wouldRefuse: false`. The trust audit event records that enforced tier, naming the demotion in `reason` — and under `NEXUS_REPUTATION_GATING=audit`, naming the demotion it would have applied. Consequence: `NEXUS_REPUTATION_GATING` and `NEXUS_FIREWALL_POLICY` are read once per process at the firewall's first use rather than on every triage or review.

`isAllowlisted` is no longer recorded when no allowlist was consulted. `IssueTriageResult.trustAssessment.isAllowlisted`, `PRTrustAssessment.isAllowlisted`, and `TrustClassificationEvent.isAllowlisted` are now optional: absent means "no allowlist was consulted", which is the state on every live path today since no source for one exists (no config field, no env var). `FirewallResult.isAllowlisted` is added with the same semantics; `FirewallResult.trust.isAllowlisted` keeps its always-boolean shape.

`HostileInputFirewall.process(input, options?)` accepts per-call `FirewallProcessOptions` — `allowlistedMaintainers` (the repository's list for this call; replaces the construction-time list and is forgotten afterwards) and `context` (the caller's access posture for this call). One shared instance can therefore serve many repositories without holding any repository's allowlist process-wide. `FirewallConfig.contentDowngrade` (default `true`, the pre-existing behaviour) and `FirewallResult.auditSink` are added. `FirewallProcessOptions` is exported. `gatePRAuthor` now takes the firewall result and the caller's reputation and returns a `Result`.
